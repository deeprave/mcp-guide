## Why

Guide's `Result` responses lean on bare imperative instruction strings ("You MUST follow these instructions", "Present this error to the user, do NOT attempt to correct") instead of the `disposition` field that already exists to carry the same meaning structurally. An unexplained command embedded in tool output is indistinguishable, from a safety-trained agent's perspective, from a prompt-injection attempt — we confirmed this directly this session when a bare filesystem-probe instruction triggered defensive pushback that a disclosed, cooperative rewrite (why → what → action) resolved immediately. `disposition` is set on only 5 of 229 `Result` construction sites; the rest repeat prose that a well-taught disposition vocabulary could replace outright. Error responses have no disposition at all today, despite there being two clearly distinct failure modes (agent-correctable vs. user-correctable) that call for opposite agent behavior — self-correct vs. stop and report — and today both get the same generic "don't attempt to correct" imperative.

## What Changes

- Define three content dispositions and their intended agent behavior: `user/information`, `agent/information`, `agent/instruction`. (A fourth constant, `AGENT_REQUIREMENTS`/`agent/requirements`, was found during this proposal's audit to have zero live usages anywhere in the codebase — plumbing only, never set by any template or code path — and has been removed rather than given new semantics; see Impact.)
- Introduce two new error dispositions, currently absent from the codebase: `agent/error` (agent-correctable, e.g. mutually exclusive arguments — cooperative "here's what to fix" tone) and `user/error` (user-correctable or not currently possible — tone explicitly discourages the agent from over-helpfully interpreting or correcting, to avoid wasting the user's time and tokens).
- Design how the agent learns this vocabulary once (a taught reference), rather than re-explaining disposition semantics in every response — resolving where that teaching lives and how/when it reaches the agent.
- Establish the principle that a correctly-set `disposition` should, in most cases, replace a paired prose `instruction` entirely rather than duplicate it, and rewrite the shared `result_constants.py` instruction constants and helper functions (`make_no_project_result`, `make_invalid_session_result`, `make_unmintable_session_result`) accordingly as a pilot.
- Audit and inventory (but do not rewrite) every `additional_agent_instructions` usage site — most are rendered mustache templates needing individual, case-by-case review — flagging them for a separate future change.
- Audit and correct the documented behavior of the `get_content` instruction-combining chain (`combine_instructions` in `src/mcp_guide/content/utils.py`), assessing which combined instructions become redundant once disposition is taught vs. which carry irreplaceable context and should be kept (reworded cooperatively).
- **BREAKING** (internal only, no external protocol change): `Result.failure()`/`Result.ok()` call sites migrated in the pilot will carry a `disposition` value and a shorter or absent `instruction`; any code or test asserting exact legacy instruction text at those specific sites will need updating.

Out of scope for this change: migrating all 229 `Result` construction sites (tracked as follow-up once the pilot pattern is validated), and rewording any `additional_agent_instructions` content (audit/flag only).

## Capabilities

### New Capabilities
- `result-disposition`: Defines the disposition vocabulary (three content dispositions plus two error dispositions), the cooperative tone/content rules for each, how the agent is taught this vocabulary, and the principle governing when `disposition` replaces `instruction`.

### Modified Capabilities
- `template-rendering`: "Centralized Instruction Resolution" currently requires a non-null type-based default instruction for every content type; this change makes that default `None` for types whose meaning is fully carried by disposition, so the requirement's scenario needs updating to reflect that a type MAY have no default instruction once its disposition is taught.
- `tool-infrastructure`: "Result Pattern Implementation" describes `Result`'s fields and `instruction` field semantics but omits `disposition` entirely, despite it being a real field this change actively expands; adds the missing disposition vocabulary and its relationship to `instruction`.
- `template-support`: "Template Error Handling" pinned a literal instruction string (`INSTRUCTION_TEMPLATE_ERROR`, "Check template syntax and available context variables") for the `RuntimeError`/template-syntax-error path in `guide_prompt.py`'s `handle_command`. Originally scoped out of the pilot (see prior note below, kept for history), brought into scope during pilot migration (task 3.2) once that call site was migrated to `disposition: agent/error` alone — the failure is agent-fixable (the agent authored or can edit the broken template) but not fixable by retrying the same call, matching `agent/error`'s "fix and retry" framing at one remove. The requirement's "Agent error instruction" scenario now requires the disposition instead of the literal string.

Other specs referencing `instruction`/`Result` were checked and found out of scope for this change: `response-metadata` (pure transport mechanics, unaffected — this change only audits `additional_agent_instructions` content, never its delivery), `session-management` (its `make_no_project_result` description is stale independent of this change — a pre-existing accuracy gap, not something this change creates or is responsible for fixing; tracked as follow-up work), `prompt-infrastructure` (requires disposition preservation through the prompt adapter — mechanism unaffected by this change, to be verified during implementation rather than spec'd here).

## Impact

- `src/mcp_guide/core/result.py` — no field changes; `disposition` values now drawn from the expanded vocabulary.
- `src/mcp_guide/result_constants.py` — `AGENT_REQUIREMENTS` and `INSTRUCTION_AGENT_REQUIREMENTS` removed (dead, zero usages, confirmed by audit); disposition constants gain two error entries; several remaining `INSTRUCTION_*` constants are rewritten or retired in favor of disposition alone, scoped to the pilot's helper functions.
- `src/mcp_guide/render/frontmatter.py` — `get_default_instruction_for_type`'s lookup table drops its `AGENT_REQUIREMENTS` entry (already done as part of the dead-code removal above).
- `src/mcp_guide/render/cache.py` — `_build_system_context` drops the unused `INSTRUCTION_AGENT_REQUIREMENTS` template-context export (already done as part of the dead-code removal above).
- `src/mcp_guide/render/frontmatter.py`, `src/mcp_guide/render/content.py` — `get_default_instruction_for_type` mapping extended for the two new error dispositions and revised wording for existing ones; `RenderedContent.disposition`/`.instruction` resolution unaffected in mechanism, only in the strings it resolves.
- `src/mcp_guide/content/utils.py` — `combine_instructions` behavior audited and documented accurately; no functional change unless the audit finds a defect.
- Pilot call sites only: `make_no_project_result`, `make_invalid_session_result`, `make_unmintable_session_result` in `result_constants.py`, plus one or two representative tool files (selected during design).
- A new agent-facing reference (mechanism TBD in design.md) teaching the disposition vocabulary once per session/process.
- Tests covering pilot call sites' exact instruction text will need updates; broader `Result` consumers elsewhere are unaffected since `disposition`/`instruction` remain optional fields.
- `openspec/adr/003-result-pattern-response.md` — amended (not rewritten) with a dated addendum, following the file's existing 2025-12-07 amendment precedent: its "Instruction Field Semantics" catalog of imperative patterns ("Present this error to the user and take no further action", "Do NOT make any changes to the project") is superseded for new code by the disposition vocabulary; the original ADR text and its historical rationale are left intact.
- Developer documentation (`docs/developer/template-rendering.md` and related authoring guides) is known to need updating for `disposition` but is explicitly out of scope for this change — tracked as the separate `update-developer-docs` follow-up change.
- Broader OpenSpec accuracy issues found during this proposal's audit but not caused by this change (e.g. `session-management`'s stale `make_no_project_result(ctx)` description, and general spec staleness/size cleanup) are explicitly out of scope here — tracked as the separate `update-openspec-specs` follow-up change.
